Agent 平台支持 ReAct 模式

如果你看到了这个文档，那实在是太幸运了，这是我在百度的最后一篇文档，

**设计目标：**在保留 Workflow 确定性执行能力的基础上，引入基于 ReAct 的 AutoAgent。由大模型负责动态规划和能力选择，由 Tool 与 Workflow 负责受控执行，并通过统一的状态、记忆和信号协议支持多轮交互与任务恢复。

## 1. 背景与设计边界
### 1.1 当前模式
当前 Agent 主要采用画布式 Workflow。用户配置节点及其连线，形成从开始节点到结束节点的固定执行路径。

![当前画布式 Workflow 示例](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=92048de31b9c4146bb926a80ac44213f&docGuid=0XM2xa_7dZuBHd "当前画布式 Workflow 示例")
|**现状问题**|**架构影响**|
|-|-|
|路径固定|系统难以根据用户问题和执行结果动态调整下一步动作。|
|编排成本高|复杂任务需要大量节点、分支和连线，配置与维护成本较高。|
|Node 依赖 Workflow|部分节点依赖完整工作流上下文，无法直接作为独立能力被模型调用。|
|跨轮状态分散|会话变量、Workflow 运行状态和执行结果缺少统一管理。|

### 1.2 目标能力
#### 动态规划
模型结合用户请求、记忆和执行结果决定下一步动作。

#### 能力复用
将 Node 封装为 Tool，并允许 AutoAgent 调用已有 Workflow。

#### 多轮执行
支持等待用户、等待事件、恢复 Workflow 和继续规划。

#### 统一治理
统一管理状态、变量、执行信号、调用轨迹和安全边界。

### 1.3 核心设计原则
* **规划与执行分离：**模型负责选择动作，Runtime 负责校验、调度和控制。
* **确定性与灵活性结合：**开放式任务使用 Tool 组合，固定业务流程继续使用 Workflow。
* **能力契约化：**Tool 和 Workflow 均需声明名称、描述、输入、输出及执行方式。
* **状态显式化：**会话、记忆、观测、规划和 Workflow 实例状态统一进入 AgentState。
* **渐进式复用：**优先通过适配层复用现有 Node 与 Workflow 引擎，避免整体重写。

## 3. 核心领域对象
### 3.1 AutoAgent
AutoAgent 是配置与运行的顶层实体，负责声明模型行为、可用能力、循环上限和记忆结构。Tool 对应原子能力，Workflow 对应确定性业务流程。

```json
{
  "id": "customer_service",
  "name": "电商客服 Agent",
  "description": "处理订单、物流及售后问题",
  "systemPrompt": "...",
  "maxLoop": 10,
  "tools": [
    {
      "id": "query_order"
    },
    {
      "id": "query_logistics"
    }
  ],
  "workflows": [
    {
      "id": "refund_workflow"
    }
  ],
  "memorySchema": [
    {
      "name": "orderId",
      "type": "string",
      "description": "当前会话关联的订单号"
    }
  ]
}
```
**配置归属建议：**AutoAgent 只保存 Tool 与 Workflow 的引用和调用契约，不直接保存完整画布数据。Node 配置和 Workflow 图结构仍由对应领域存储维护，运行时按 ID 加载，避免重复数据和版本不一致。

### 3.2 Tool
Tool 是可被 Planner 直接选择的原子能力。其底层可以复用现有 Node，但必须具备独立的输入输出契约，不能依赖完整 Workflow 上下文。

**参数校验**

校验必填项、类型和调用权限。

**参数补全**

合并模型入参、固定配置、记忆和运行时信息。

**Node 执行**

通过 Adapter 调用现有 Node 执行器。

**结果标准化**

输出统一 Observation 并按规则更新记忆。

#### Tool 参数来源
|**类型**|**来源**|**示例**|
|-|-|-|
|固定配置|创建 Tool 时配置|API 地址、鉴权方式、知识库 ID、模型参数。|
|动态输入|Planner 调用时提供|订单号、查询条件、用户问题。|
|记忆变量|AgentState.memory|用户 ID、当前订单号、已确认选项。|
|运行时参数|平台自动注入|会话 ID、调用链 ID、用户身份和超时配置。|

#### Tool 定义示例
```json
{
  "id": "query_logistics",
  "name": "查询物流",
  "description": "根据订单号查询物流状态",
  "executor": {
    "type": "node",
    "resourceId": "e6f2b050-482f-4e11-9b22-5347e6ec9b04"
  },
  "inputs": [
    {
      "name": "orderId",
      "type": "string",
      "required": true,
      "description": "订单号"
    }
  ],
  "inputMapping": [
    {
      "source": "inputs.orderId",
      "target": "node.params.orderId"
    }
  ],
  "outputs": [
    {
      "name": "logisticsStatus",
      "type": "string"
    },
    {
      "name": "company",
      "type": "string"
    }
  ],
  "outputMapping": [
    {
      "source": "result.status",
      "target": "outputs.logisticsStatus"
    },
    {
      "source": "result.company",
      "target": "outputs.company"
    }
  ],
  "memoryMapping": [
    {
      "source": "outputs.logisticsStatus",
      "target": "memory.logisticsStatus"
    }
  ]
}
```
### 3.3 Workflow
Workflow 用于承载退款、补偿等路径明确且需要确定性执行的业务流程。AutoAgent 负责选择和启动 Workflow，Workflow 引擎负责其内部节点执行。

|**维度**|**Tool**|**Workflow**|
|-|-|-|
|能力粒度|单一、原子能力|多节点业务流程|
|执行路径|单次调用后返回 Planner|按画布定义确定性执行|
|交互能力|通常同步返回结果|可暂停、等待用户或事件后恢复|
|典型场景|查询订单、检索知识、调用接口|退款、补偿、审批、转人工|

#### Workflow 调用契约
现有父子 Workflow 仅支持传递单一 `query`。本方案将 Workflow 升级为显式的多入参、多出参能力，图结构继续按 Workflow ID 从数据库加载。

```json
{
  "id": "refund_workflow",
  "name": "退货流程",
  "description": "处理用户退货申请",
  "inputs": [
    {
      "name": "query",
      "type": "string",
      "required": true
    },
    {
      "name": "orderId",
      "type": "string",
      "required": true
    },
    {
      "name": "logisticsStatus",
      "type": "string",
      "required": false
    }
  ],
  "outputs": [
    {
      "name": "answer",
      "type": "string"
    },
    {
      "name": "refundId",
      "type": "string"
    }
  ]
}
```
#### Workflow 变量隔离
一个 AutoAgent 可以同时配置多个 Workflow。Workflow 内部变量应按 `agentId + workflowId + instanceId` 建立命名空间。运行时只向目标实例注入其输入变量，完成后仅按输出契约提取指定变量，避免不同 Workflow 共用会话变量时发生覆盖。

### 4.2 Planner 协议
Planner 的输入只包含完成决策所需的信息，不直接传入完整 Node 配置或 Workflow 图结构，以控制上下文长度并降低模型理解成本。

#### 请求示例
```json
{
  "query": "我要退货",
  "systemPrompt": "...",
  "memory": {
    "uid": "1001",
    "orderId": "888"
  },
  "tools": [
    {
      "id": "query_logistics",
      "name": "查询物流",
      "description": "根据订单号查询物流状态",
      "inputs": [
        {
          "name": "orderId",
          "type": "string",
          "required": true
        }
      ]
    }
  ],
  "workflows": [
    {
      "id": "refund_workflow",
      "name": "退货流程",
      "description": "处理用户退货申请",
      "inputs": [
        {
          "name": "orderId",
          "type": "string",
          "required": true
        }
      ]
    }
  ],
  "observations": []
}
```
#### 响应示例
```json
{
  "thought": "退货流程需要先确认物流状态",
  "action": {
    "type": "TOOL",
    "targetId": "query_logistics",
    "arguments": {
      "orderId": "888"
    }
  }
}
```
### 4.3 统一执行结果
Tool 与 Workflow 均返回统一的执行结果结构。Runtime 根据 `signal` 判断继续规划、等待外部输入、结束或进入异常处理。

```json
{
  "success": true,
  "sourceType": "TOOL",
  "sourceId": "query_logistics",
  "summary": "查询物流成功",
  "outputs": {
    "logisticsStatus": "运输中",
    "company": "顺丰"
  },
  "signal": "CONTINUE",
  "message": ""
}
```
|**Signal**|**Runtime 行为**|
|-|-|
|`CONTINUE`|记录 Observation，并携带新结果进入下一轮 Planner。|
|`FINISH`|任务完成，保存结果并向用户返回最终响应。|
|`WAIT_USER`|保存当前状态和 Workflow 实例，向用户输出提示，下一轮优先恢复该实例。|
|`WAIT_EVENT`|保存状态并等待异步事件；事件到达后恢复执行。|
|`ERROR`|根据错误是否可恢复，决定重试、重新规划或终止。|
|`CANCEL`|终止当前动作或 Workflow，并清理对应运行状态。|

### 4.4 停止条件
* Planner 返回 `FINAL`，或执行结果返回 `FINISH`。
* 循环次数达到 `maxLoop`。
* 连续动作未产生有效的新信息。
* 缺少必要参数，需要等待用户补充。
* Tool 或 Workflow 返回不可恢复错误。
* 任务触发权限、安全或业务边界限制。

### 5.3 存储边界
|**数据**|**存储建议**|**说明**|
|-|-|-|
|AutoAgent 配置|Agent 配置库|保存 Prompt、能力引用、循环上限和记忆定义。|
|Tool 定义|Tool Registry|保存调用契约、执行器引用和参数映射。|
|Node 配置|现有 Node 配置库|由 Node Adapter 根据资源 ID 加载。|
|Workflow 图结构|现有 Workflow 配置库|AutoAgent 不重复保存画布数据。|
|AgentState|会话状态存储|支持跨轮读取、恢复和过期清理。|
|WorkflowInstance|流程实例存储|支持暂停、等待用户或事件后继续执行。|
|Trace|日志与观测存储|用于调试、审计、评估和成本分析。|

## 6. 关键执行链路
### 6.1 Tool 调用
1. Planner 选择 Tool，并生成结构化参数。
2. Tool Runtime 校验参数、权限和调用限制。
3. Runtime 从记忆和上下文补全缺失参数。
4. Node Adapter 加载对应 Node 配置并完成参数映射。
5. 现有 Node 执行器运行底层能力。
6. Runtime 将原始结果映射为标准输出和 Observation。
7. 按 `memoryMapping` 更新记忆，并进入下一轮 Planner。

### 6.2 Workflow 调用与恢复
1. Planner 选择 Workflow，并提供显式输入参数。
2. Workflow Runtime 创建实例和独立变量命名空间。
3. 输入参数写入实例变量，Workflow 引擎从开始节点执行。
4. Workflow 返回输出及 Signal。
5. 如果为 `WAIT_USER` 或 `WAIT_EVENT`，Runtime 保存实例并结束当前请求。
6. 下一轮请求或异步事件到达时，Runtime 优先恢复对应 Workflow 实例。
7. Workflow 完成后，仅提取输出契约声明的变量并写回 AgentState。

## 7. 实施路径
**阶段一：Tool 闭环**

实现 AgentState、Planner 协议、ReAct 循环、Tool Registry 和 Node Adapter，优先接入 API、代码及知识库节点。

**阶段二：Workflow 接入**

实现多入参、多出参、变量命名空间、实例存储以及同步调用。

**阶段三：中断恢复**

支持 WAIT_USER、WAIT_EVENT、异步事件和跨轮恢复。

**阶段四：平台治理**

补齐权限、审计、调试、评估、版本管理和运行成本控制。

## 8. 决策事项
|**决策主题**|**需要确认的问题**|
|-|-|
|模型动作协议|统一使用平台 JSON 协议，还是兼容不同模型原生的 Tool Calling 协议？|
|Tool 与 Node 的关系|Tool 引用已有 Node，每一个 Node 都需要有一个 Node Config 的 json|
|Workflow 调用模式|仅支持同步执行， 不支持跨轮恢复，|
|输出写回策略|Tool 和 Workflow 输出默认写入记忆，按照显式映射写入|
|实例并发|一个会话不允许同时存在多个处于等待状态的 Workflow 实例， 如果用户问题切换，上一个 workflow 的等待状态就自动流转为完成|
|恢复路由|用户新消息到达时，直接恢复已有 Workflow，让workflow判断是否需要退出|
|调试可见范围|最好是有一些追踪的手段，例如sql 这些，可以知道在干嘛，主要用来查询|
